NEW MAJOR CONCERNS

R1. IN THE RELEASED CODE, EVERY REPORTED PERFORMANCE FIGURE IS PRODUCED BY SELECTION ON THE TEST SET.

I treat the repository as authoritative because the manuscript does: the code-sharing statement calls it "the source code used to generate all results reported in this manuscript". If that is not true of these numbers, the right answer is to say so and release the code that is. I read the notebooks and their saved outputs but executed nothing.

(a) Fusion weights. In run_multimodal_final.ipynb the grid computes a validation AUC and discards it:

val_auc = roc_auc_score(y_val, combined_val) # computed, never used for selection
res = evaluate(y_test, combined_test, "", verbose=False)
if res['auc'] > best_auc:
best_auc = res['auc']; best_weights_auc = (w1, w2, w3)

The saved output reads "Total combinations tested: 186" and "Best by AUC: MRI=0.23, M2=0.63, M3=0.14", the weights reported in the manuscript. They are the argmax of test AUC over 186 candidates on 62 subjects with 7 positives, not of validation AUC as Eq (33) and bullet 3 of the transparency subsection state.

(b) Threshold. evaluate() sets the threshold by Youden's J on the labels passed to it, and every call site passes y_test (roc_curve, then np.argmax(tpr - fpr)). So the confusion matrix TP = 6, FP = 7, TN = 48, FN = 1, and hence the new PPV, NPV and NNS, come from a threshold fitted on test labels. Bullet 4 places this on validation.

(c) Checkpoints. In advanced_anxiety_questionnaire_prediction.ipynb the best epoch is chosen by test AUC under a variable named val_auc:

val_probs = proto_net.predict_proba(X_test_t, prototypes)[:, 1].cpu().numpy()
val_auc = roc_auc_score(y_test, val_probs)
if val_auc > best_proto_auc:
best_proto_auc = val_auc; best_state = {...}

advanced_static_prediction.ipynb does the same, and also picks among eight models by test AUC. Bullet 5 places early stopping on validation.

(d) Polarity. Both notebooks flip the sign of their predictions when test AUC falls below 0.5 (rf_inverted, proto_inverted),: the saved outputs read "ProtoNet AUC: 0.7818 [INVERTED]" for the questionnaire module and "ProtoNet AUC: 0.7065 [INVERTED]" for the phenotypic one, so the un-inverted values are about 0.218 and 0.294, both far worse than chance. Those inverted probabilities are written to module2_full_features.csv and module3_full_features.csv and consumed by the fusion notebook. I could not match any reported unimodal AUC (0.7455, 0.7766, 0.6961) to an un-inverted output, and 0.6961 appears in the questionnaire notebook's output rather than the phenotypic one. Please reconcile each reported value with the code and say whether its sign was set using test labels.

(e) Modules 2 and 3 have no validation partition. Both notebooks stack train and validation into X_trainval and train on it, with the saved output "Original: 242 samples (31 pos)". Validation data is therefore training data for two of three modules, so the val_auc in (a) is partly in-sample and would have been uninformative even if used. The transparency subsection presents that partition as the basis of six decisions; on this code it was not held out.

Together these mean the reported AUC 0.8935, F1 0.600, the weights 0.23/0.63/0.14 and the clinical utility metrics are not out-of-sample estimates. I am not suggesting anything about intent, and the cell headed "FINAL RESULTS (No Data Leakage)" tells me the question was considered. My point is narrower: the procedure implemented is not the procedure described, and the gap is large enough to change what the numbers mean.

Please either re-run with every selection decision confined to a genuinely held-out validation partition (checkpoint, polarity, classifier choice, weights, threshold), report whatever the test metrics turn out to be, and revise all claims to match; or state that the repository is not the code behind the reported numbers and release the code that is. On cost, a point in your favour: the fusion grid already stores val_auc at every point, so selecting on it is a one-line change, though the module-level decisions do need re-running. A lower but honest number would not by itself make this unpublishable in PLOS ONE, which does not assess impact; publishing the current numbers with the current account of how they were obtained is what will not work.

The new Ablation paragraph asserting that the disproportionate three-way gain is "not an artifact of overfitting" is not supportable as written: the three-way weights were tuned on the test set over 186 candidates while the pairwise combinations were not tuned at all, so that comparison is not like-for-like.

R2. THE CORRECTED ATTENTION DESCRIPTION MAKES EACH PREDICTION DEPEND ON THE OTHER SUBJECTS SCORED WITH IT.

On my previous M2 the authors are right and I accept the correction. The implementation is batch-level:

def forward(self, x):
q, k, v = self.query(x), self.key(x), self.value(x)
attn = torch.softmax(q @ k.T * self.scale, dim=-1)
return attn @ v + x

With x of shape (n, 64), q @ k.T is (n, n) and the softmax is non-degenerate, as the revised text says. My original reading followed the manuscript, which described a per-sample operation.

What follows is not that point restated but a consequence of the correction, invisible while the text described a per-sample operation. The minimum I ask is a statement of the inference batching policy and test metrics at batch size 1; removing the layer is an option, not a requirement. Because attn @ v mixes value vectors across samples, each subject's embedding is a weighted combination of the others in the same forward pass, and the test set is scored in one pass (X_test_t holds all 62 subjects). Three consequences:

1. Inference is transductive: each test subject's score depends on the other 61, so the metrics describe a model that sees the whole test cohort at once.

2. The model cannot be run as the paper motivates it. At n = 1 the softmax is over one element, equal to 1, and the layer reduces to V + x, so the reported performance is not attainable in per-subject screening.

3. Splits are at family level, so intact twin pairs sit in the same partition and cross-sample attention lets a subject's representation draw on their co-twin's features inside the forward pass, the mechanism the family-level split exists to prevent. Since 118 of 422 subjects were excluded for incomplete data an unknown number of pairs are broken; please report how many intact pairs are in the test partition.

Fig 4 gives no indication that the attention is batch-level; a block diagram may legitimately omit the batch dimension, so this is only a suggestion to annotate it. One knock-on effect: because the output is not a function of one subject's features alone, Shapley additivity does not hold, so resolving this is a prerequisite for the SHAP analysis in R6.

R3. THE TWIN-AWARE DATA SPLITTING SUBSECTION HAS BEEN REMOVED.

The original had a named subsection: "Twin-Aware Data Splitting. To prevent co-twin information leakage, data are split at the family level. Twin pairs are assigned entirely to one of the following sets: Training 60% (180; 24 positive), Validation 20% (62; 7), Test 20% (62; 7)." In the revision that heading and text are gone, the phrases "Twin-Aware Data Splitting" and "split at the family level" do not appear, and no split proportions are stated. What survives is the orphaned sentence "This strategy preserves class distributions, avoids inflated performance due to shared genetic information..." with no antecedent.

The family-level split is the paper's headline contribution and the Abstract, Introduction and Conclusion all rest on it. It now has no description in the Methods, and the split files are not in the repository, so it can be neither read nor verified. I assume this was accidental, most likely when the 478/422/304 paragraph was inserted. Please restore it with the number of intact pairs per partition, and release the split files.

R4. TABLE 3 CONTRADICTS THE METHODS AND CODE.

Table 3 is a good addition but does not match the manuscript it sits in.

Module 2: Table 3 gives Adam, LR 5e-4, 200 epochs, batch 32, dropout 0.3. The Methods give AdamW, initial LR 0.002, one-cycle peaking at 0.005, 150 epochs, dropout 0.2. The code agrees with the Methods: AdamW(lr=0.002, weight_decay=0.01), OneCycleLR(max_lr=0.005, epochs=150, steps_per_epoch=1), Dropout(0.2), full-batch with one step per epoch. Batch size matters beyond reproducibility here, because of R2.

Module 3 diverges the same way: the code uses AdamW(lr=0.001, weight_decay=0.02), OneCycleLR(max_lr=0.003, epochs=250) and full-batch training against Table 3's Adam, 5e-4, 200 epochs, batch 32.

Module 1: Table 3 gives "Focal Loss (gamma = 2)" where the Methods say cross-entropy; "SMOTE + class weights" where the Methods describe additive Gaussian noise and feature dropout and never mention SMOTE; "Embedding dimension 128" where the Methods describe 384 projected to 768.

Three rows have no counterpart in the code: isotonic calibration (R7), "Class weights (1:7)", where the code uses copy-paste augmentation with FocalLoss(alpha=0.75), and early-stopping patience, where the code keeps the best-ever checkpoint. Limitations item 8 also generalises SMOTE to the whole framework against Table 3's own footnote, and the sentence introducing Table 3 says it "summarizes the hardware specifications", which no table does.

R5. THE FUSION-WEIGHT JUSTIFICATION CONTRADICTS EQ (31) AND THE CODE.

The new paragraph says the weights were searched in questionnaire [0.30, 0.80], MRI [0.10, 0.50], phenotypic [0.05, 0.30], with "more than 9,000 unique combinations" at step 0.02. Eq (31) gives w1 [0.15, 0.45], w2 [0.35, 0.65], w3 [0.10, 0.45], and the code matches Eq (31). The stated ranges are not merely different, they are infeasible: at step 0.02 the questionnaire and MRI grids fall on even hundredths and the phenotypic grid on odd ones, and two even values plus one odd cannot sum to 1.00, so no admissible point exists and none of the reported weights (0.23, 0.63, 0.14) lie on those grids. The real count is in your own output, "Total combinations tested: 186". Please correct it to the ranges searched and to 186.

R6. THE SHAP ANALYSIS DOES NOT MATCH THE SCRIPT.

The interpretability section is the right addition but cannot be relied on as it stands.

- Feature count: the text says "Among the 88 questionnaire features analysed" while Module 2 uses the top 40 (Methods, Table 3, and top_k = 40 in the code).



- Stated method: the manuscript says "the classical neural network architecture is not suitable for calculating SHAP values" and that random forest surrogates were trained. shap_analysis.py uses shap.KernelExplainer(wrapper.predict_proba, background) directly on the network, with no surrogate; KernelExplainer is model-agnostic, so the justification does not hold either way. If surrogates were used, report their fidelity to the network's predictions.

- The released script does not compute attributions for the model's prediction: the prototype computation is commented out and replaced by probs = torch.softmax(embeddings, dim=1)[:, 1] under the comment "For now, using a simplified version", a softmax over the embedding rather than the prototype cosine similarities that define the output. The train/validation construction is also a placeholder: X_trainval = np.vstack([X_train]) # Use your actual train+val here. If Figs 8 to 11 came from other code, please release it.

- The rankings diverge. The three highest-correlated features (pSCAS32, pSCAS18, pSCAS30), on which the Construct Overlap subsection rests, are absent from the SHAP top ten, whose leading feature SCAS19 is not in the correlation list. The lists are not disjoint (pSDQ13 and SCAS15 appear in both) but the divergence at the top is complete, and both are presented as the module's most influential features.

R7. THE CALIBRATION SENSITIVITY ANALYSIS IS NOT IN THE CODE.

The Abstract states that calibrated module outputs are fused, and the new paragraph reports isotonic regression against Platt scaling with "mean calibration error differences below 0.02 across decile bins". The strings isotonic, calibrat and platt appear in none of the five notebooks, and the fusion notebook combines the raw module probabilities directly. No per-module numbers, table or reliability diagram is given, and decile bins on 7 positives would not be informative anyway. Please release the code and numbers, or withdraw the sensitivity claim and the word "calibrated" from the Abstract and Eq (28).

R8. PREVALENCE IS MISSTATED IN THE CLINICAL-UTILITY SUBSECTION.

It twice reads "At the QTAB prevalence of 11.3% incident anxiety (38/304)". 38/304 is 12.5%, the figure given correctly in the Methods; 11.3% is the test-set positive rate (7/62), and at 12.5% the NNS is 9.3. Your response records this as a correction, "NNS: ~9 corrected to ~10", so the original value was right. Please state which prevalence the utility metrics assume, since PPV depends on it.
